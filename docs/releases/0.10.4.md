# OpenPrintDeploy 0.10.4

Fixes duplex configuration on OPD-deployed shared printers, prepares separate
core-driver dependencies through the SYSTEM service, and adds targeted remote
repair of a client's printer connections. This release includes the fixes
validated in the beta 2 pilot and the beta 3 Type 4 repair fix.

## Shared-printer configuration and driver preparation

- Create normal silent Windows shared-printer connections after driver
  preparation, preserving server device options instead of forcing a local
  rendering-driver substitution that can break duplex/finishing capabilities.
- Bundle every declared core driver's complete signed package with the vendor
  package. Stage core packages separately under SYSTEM before installing the
  vendor driver; Windows validates each package's signature and catalog.
- Include core-driver versions and contents in the export cache fingerprint,
  so a server's Windows core update invalidates an unchanged vendor bundle.
- Verify that dependencies are Windows-published in the client Driver Store,
  or that a sufficient registered core version exists. A successfully staged
  package remains usable even if Windows retains an older default registration.
- Check live server driver and core-package readiness before disconnecting an
  existing queue. Incomplete preparation defers repair without removing it.
- Verify the actual server share and its vendor driver through server-side
  enumeration. A Type 4 client's Microsoft enhanced Point and Print driver can
  legitimately differ from the prepared vendor driver. This supported mapping
  no longer causes a false migration failure; genuine server/package identity
  changes still defer repair before disconnecting.
- Use a fresh protected client preparation cache. Do not adopt legacy cache
  contents after permissions have allowed untrusted writes. This may repeat
  driver preparation once; it does not reinstall every connection.

## One-time migration and remote repair

Existing, still-assigned OPD-managed connections migrate once from the legacy
connection mode. Completed migration revisions survive later client upgrades,
including beta-to-stable upgrades. Unfinished repairs retry after preparation
succeeds. Personal printers outside OPD management are excluded, and global
removal rules take precedence. Pending user print jobs defer that queue's repair.

Repair saves the default printer and supported standard printing preferences
before disconnecting. Durable snapshots recover interrupted repairs; a
connection already re-added by normal sync is not disconnected again merely to
finish restoring its saved preferences.

On **Clients -> computer -> user**, administrators can use **Repair printer
connections** for one device/user. The client repairs its currently assigned
OPD-managed queues and reports Pending, Running, Completed or Failed. Retrying
a failed request resumes unfinished queues; a new request after completion
deliberately repairs eligible connections again. Requests and reports are
authenticated, correlated and audited. Older clients require an update before
this control is available.

## Removal history

Suppress repeated confirmations that a forced-removal printer is already absent,
while continuing to enforce the rule. Real removals, changed failures and
recovery remain recorded. Older duplicate absence entries are collapsed in the
admin view without deleting audit history.

## Upgrade

1. Back up the server database and customized configuration, then upgrade the
   **server MSI first**. The server bundles the matching client MSI for
   preconfigured downloads from its admin page.
2. Upgrade clients using that preconfigured download or the existing Intune
   server URL, certificate pin and allowed-server settings.
3. Clients upgrading from 0.10.3 perform their one-time connection migration.
   Beta clients retain completed migrations and resume any unfinished repairs.

The server applies the repair-status/capability database migration introduced
in beta 1, using the existing pre-migration SQLite backup behaviour. Existing
0.10.3 clients can continue normal sync during a staged client rollout; the new
repair and dependency handling require updated clients. A new client defers
core-dependent preparation against an older server that omits core metadata,
so upgrade the server first.

Windows Installer ProductVersion is **0.10.4**. Same-version upgrades support
moving from either 0.10.4 beta to stable without uninstalling first. The
applications display **0.10.4**. Packages are self-contained Windows x64 MSIs;
they remain unsigned with the current build configuration. Driver-package
signature validation is independent of MSI signing.

Set `ConnectionRepairsEnabled=0` under
`HKLM\SOFTWARE\OpenPrintDeploy\Client` to pause connection repairs if required.
Vendor-private finishing/accounting settings may reset on reconnection; the
saved settings restore supported standard preferences rather than stale vendor
private configuration.

## Validation

- 358 automated tests pass in Release with dependency auditing, covering
  migration readiness, durable recovery, package/dependency handling, remote
  repair authorization and replay, native API bindings, and removal history.
- The installed beta 2 client and SYSTEM service completed driver preparation
  for all 13 managed queues and a successful sync without new service warnings
  or errors after the upgrade. All migration revisions are complete.
- A6 Office, Science Lab Tech, Black Follow Me and Colour Follow Me retain
  duplex options. Physical double-sided printing was confirmed on all four
  during the pilot.
- The complete signed Lexmark/Microsoft package-installation pipeline passed
  an elevated native pilot. Beta 2 installer payloads were extracted and
  checked against the built applications, service and bundled client MSI.
- The Type 4 identity issue was reproduced with normal Windows client rendering
  and corrected. A controlled VCE Staffroom reconnect preserved duplex, default
  printer and standard preferences; replaying recovery did not reconnect again.
- A second laptop's beta 2 log identified three safely deferred Type 4 queues
  that the user confirmed still print. A post-fix sync log from that second
  laptop was not supplied at release time; the Type 4 fix was validated with
  regression tests and the controlled native pilot above.

Use the normal staged rollout for other printer models and configurations;
the pilot covers the queues above, not every vendor's private driver features.
