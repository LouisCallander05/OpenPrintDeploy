# OpenPrintDeploy 0.10.4-beta.1

**Beta prerelease — deploy to a small pilot group before wider rollout.**

This beta fixes shared-printer duplex configuration, repairs existing legacy
connections once, adds an administrator-triggered remote repair action, and
reduces repeated printer-removal history entries.

## Printer connections and automatic repair

- Connect shared queues using standard silent Windows driver selection instead
  of forcing mismatched local-driver rendering. The SYSTEM driver service still
  prepares approved packages first, so users do not need local administrator
  rights for driver installation.
- Reconnect existing, still-assigned OPD-managed connections once using a saved
  per-user connection revision. Routine client version changes do not trigger
  repeated reinstalls. Previously adopted queues already managed by OPD are
  included; personal queues outside OPD management are excluded.
- Verify driver readiness and the live server before disconnecting. Preserve
  the default printer and supported standard preferences, and retain durable
  recovery snapshots for interrupted repairs. Pending user print jobs block
  that queue's repair.

## Remote repair from the server

On **Clients → computer → user**, **Repair printer connections** queues a repair
for that device/user's OPD-managed, currently assigned queues. The upgraded
client receives it on its next authoritative sync; offline users pick it up
when they reconnect. The page shows Pending, Running, Completed or Failed.

Completed queues are recorded locally so restarts or lost acknowledgements do
not repeat them. **Retry failed repairs** reuses the request and retries only
unfinished queues. A new request after completion deliberately repairs all
eligible queues again. Global removal rules always take precedence.

Administrator authorization is required. Requests and acknowledgements are
correlated by request ID, authenticated user and stable device identity. The
device identifier remains routing metadata, not machine attestation. Older
clients show an update-required message until upgraded and synced.

## Removal history and packaging

- Suppress repeated "already absent" confirmations while continuing to enforce
  removal rules. Actual removals, changed errors and recovery remain recorded.
- Collapse older duplicate absence confirmations in the admin view without
  deleting audit records. Unchanged removal failures no longer create an event
  on every sync.
- Clear WiX intermediate caches during publishing so repeated builds cannot
  silently reuse an older installer payload.

## Upgrade

Upgrade the server MSI, then the client MSI. The server bundles the matching
client installer for preconfigured dashboard downloads. Preserve the existing
server URL, certificate pin and allowed print servers. New remote-repair
controls enable after a capable client completes a sync.

The server applies an EF database migration for repair status and capability
metadata using the existing pre-migration SQLite backup behavior. Existing
profiles run the one-time connection migration when their upgraded tray next
syncs. Set `ConnectionRepairsEnabled=0` in
`HKLM\SOFTWARE\OpenPrintDeploy\Client` to pause connection repairs.

Windows Installer records this beta as numeric version **0.10.4**; applications
display **0.10.4-beta.1**. Same-version upgrades remain enabled for subsequent
0.10.4 betas and the stable release. These packages remain unsigned unless a
signing certificate is configured for the build.

## Validation and beta limits

327 automated tests pass in Release configuration with dependency auditing,
including real HTTP repair delivery/reporting, administrator authorization,
queue scope, failure retry, replay/restart recovery, durable progress and
removal-history handling. Installer payload hashes were also checked against
the built applications during local pilot preparation.

Pilot checks recovered duplex capabilities and confirmed double-sided printing
on two Follow Me queues. Wider validation is still required: a full installed
server/client remote-repair run, fresh driver installation under organizational
restrictions, and server-side driver updates. Vendor-specific finishing options
and accounting preferences may reset when reconnecting; validate these in the
pilot. This beta is not yet approved for broad production rollout.
